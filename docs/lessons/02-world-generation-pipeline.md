# 第二课：让每个 Chunk 独立知道整个世界

旧项目生成树或洞穴时会先准备周围 Chunk，再让笔刷直接修改邻块。这种做法容易写出第一版，但会让生成顺序、并行调度、缓存和网络请求彼此纠缠。

OpenVoxel 换了一个问题：不是“我怎样修改邻居”，而是“哪些世界坐标特征有资格影响我”。

阅读顺序：

1. `packages/blocks/data/identities.yml`、`data/catalog.yml` 与 `data/blocks/` 定义全部内建身份、方块类型和有限状态；生成工具把它们编译为 `generated/block-catalog.json`，`@openvoxel/blocks` 再构造生成、模拟和渲染共享的受检查注册表。
2. `generation/terrain.vel` 把种子变成气候、高度与密度，观察二维宏观地貌和三维局部扰动如何叠加。
3. `ColumnPlanner` 展示同一水平 Chunk 的 `ColumnCache` 如何跨垂直层复用，再由岩体、地表和植物三个阶段共同读取。
4. `generation/features.vel` 从洞穴锚点开始阅读，注意每个随机流都由功能和世界坐标命名。
5. 比较树木与矿脉：形状不同，但“扩展查找锚点，只写目标 Chunk”的边界相同。
6. 回到 `generator.vel`，完整顺序只有基础岩体、洞穴、流体、矿物、地表、植被六个调用。
7. 最后查看固定种子、稀有矿物和跨边界树冠测试，理解算法描述如何变成可执行契约。

洞穴仍然遵守“重放特征，只写目标 Chunk”，但不会为每个相邻 Chunk 重新推演整条路径。一个世界内的 `CavePlanner` 按所有者坐标缓存连续球体序列和整体包围盒；目标 Chunk 先拒绝不相交的计划，再检查剩余球体。缓存有固定上限且随 `WorldGenerator` 生命周期存在，淘汰只损失速度，不改变任何生成结果。

地形柱也是同一原则。同一个 `(chunkX, chunkZ)` 无论生成多少个 Y 层，温湿度、生物群系和地表高度都不变，因此 `ColumnPlanner` 用不含 Y 的键保存 64 个最近使用的水平结果。它不缓存最终 Chunk，也不接受其他区块写入；满了只淘汰最久未使用项，下次仍可从种子得到逐位相同的结果。

最重要的可迁移结论是：确定性不是“每次使用同一个 seed”这么简单。真正的确定性要求每个子系统有独立随机命名空间、每个跨区结构有稳定所有者、每个阶段有固定覆盖规则，并且持久化清楚记录生成器版本。
